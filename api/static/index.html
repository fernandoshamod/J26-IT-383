Where the data comes from. No public event-duration dataset exists, so the models train on 800 synthetic past events from a documented generator, calibrated and validated with four public datasets (Kaggle food delivery, Sri Lanka Met Department rain gauges, Olist e-commerce, SiP task estimates). The same pipeline retrains unchanged on the industry partner's records. Booking details for this demo day (guests, venue, vendor history) are declared inputs.
Live · Constraint checks

Conflicts

The current plan re-checked by an independent verifier (not the solver that made it), plus every live divergence between plan and reality. Nothing is changed without a call from you.

Cross-event checks are on. Resources are scheduled on one shared timeline for every event in the calendar, so a crew or vendor booked by two events can never be double-booked — the solver sees both at once.
Live · Signature capability

Disruption console

Disruptions are detected, not typed in: from late check-ins and from check-ins that never arrive. The twin then simulates the knock-on effect of doing nothing and re-optimises the rest of the day — so you see the damage, and the fix, before you make the call.

Watching Every figure below is computed live by the engine
Why simulate before re-cueing? A delay does not stay where it lands. It propagates along dependencies and competes for the same staff and kit. The discrete-event simulation shows what doing nothing would cost; the CP-SAT re-optimiser shows the best alternative; you decide.
