# PP1 Task 2: standalone vendor conflict proof of concept

This directory is isolated from the production React/FastAPI recommendation flow. The module does not load saved packages, alter the category compatibility matrix, change ranking weights, call a production endpoint, or retrain the Random Forest. All 12 bundled cases are **SYNTHETIC_TEST**; the two real-looking option/vendor IDs in the presentation are verified only as existing identities in the current synthetic option table.

## Inputs and evidence

[conflict_engine.py](./conflict_engine.py) accepts an in-memory case with an event interval, selected assignments, optional event-specific pair evidence, event-specific availability, and optional vendor equipment/crew limits. All times require timezone offsets and use half-open intervals. Pair lookup sorts the two vendor IDs; a category rule is never accepted as vendor-pair evidence. For synthetic pair evidence, the record must name the current event, outcome, source, timestamp, and `SYNTHETIC_TEST` status. A claimed `REAL_PUBLIC` direct observation additionally requires a source URI and verified status, but this proof of concept cannot independently authenticate an external submitter. No bundled record is verified real-world collaboration.

The scoped result is `COMPATIBLE_WITH_EVIDENCE`, `CONFLICT_WITH_EVIDENCE`, or `VERIFICATION_REQUIRED`. A conflict dominates pending evidence; otherwise any unknown produces pending. `venue_suitability` is separately always pending for the other team's component, so a scoped compatible result is **not** a claim of complete feasibility or booking readiness.

## Windows execution

From this directory:

```powershell
& 'D:\Vendor-Intelligence-System\venv\Scripts\python.exe' -B -m unittest -v test_conflict_engine.py
& 'D:\Vendor-Intelligence-System\venv\Scripts\python.exe' -B evaluate.py
& 'D:\Vendor-Intelligence-System\venv\Scripts\python.exe' -B demo.py
```

`-B` avoids writing Python bytecode. [evaluation_results.json](./evaluation_results.json) and [demo_output.txt](./demo_output.txt) were generated by successful runs; their `--write-results` and `--save` flags use exclusive creation and refuse to overwrite existing files. The evaluation reports local in-process timing, not API or deployed response time.

## Implemented checks

- Symmetric, event-specific, provenance-aware vendor-pair evidence lookup; contradictory/unknown evidence remains pending.
- Same-vendor overlapping services when the known staffing constraint forbids multitasking.
- Same-vendor setup/service/teardown overlap under an explicit exclusive-crew constraint.
- Event-specific availability interval coverage; unknown or unsupported evidence remains pending.
- Shared equipment/crew peak demand over overlapping occupancy intervals against documented fixture limits. Missing limits remain pending.
- Venue-dependent constraints remain outside this engine.

The source [synthetic service options](../../hybrid_simulation_v1/synthetic_service_options.csv) supply setup minutes, power and space estimates, but no teardown duration or shared-equipment inventory. The latter values in [fixtures.json](./fixtures.json) are controlled simulation assumptions, never vendor facts. Power and space are venue-dependent and are deliberately not compared to invented venue limits.

## Reproducibility and validation

[fixtures.json](./fixtures.json) contains 12 hand-authored expected statuses independent of the engine. [test_conflict_engine.py](./test_conflict_engine.py) validates these, source option IDs, symmetric lookup, unknown handling, time coverage, resource contention, deterministic output and malformed inputs. [evaluate.py](./evaluate.py) computes the measured case outcomes and conflict metrics. See [limitations](./limitations.md) before citing any result.
