# PP1 Task 2 limitations and interpretation

- The 12 scenarios, pair outcomes, availability intervals, exclusive-crew rules and equipment capacities are **SYNTHETIC_TEST fixtures**. Hand-authored expected labels give known outcomes for software checks, not real-world ground truth.
- Existing [sample collaboration rows](../../hybrid_simulation_v1/synthetic_collaboration_scenarios.csv) are random simulated outcomes tied to SIMEVT events. They are deliberately not imported. The present engine requires event-matching pair evidence and ignores a different event's record.
- The existing [service-category matrix](../../vendor_compatibility_matrix.csv) measures category heuristics, not named-vendor collaboration. It is shown in the demo only as context and never decides the pair result. It may be constant for packages with the same required categories.
- The current source [option table](../../hybrid_simulation_v1/synthetic_service_options.csv) has simulated setup minutes, power and space fields. It lacks teardown duration, inventory ownership/quantity, confirmed schedules, and actual vendor quotes. Teardown and shared equipment in fixtures are invented **only for testing**. No venue power/space decision is made.
- A supplied `REAL_PUBLIC` record is structurally checked but its authenticity and meaning cannot be independently verified by this standalone module. The returned `is_real_world_collaboration_confirmed` flag remains false. Trusted acquisition and human adjudication are needed before using such evidence.
- Event availability requires an event ID and covering interval, but genuine vendor confirmation and changing calendars are not available. A simulated `available` fixture is not a booking.
- A scoped compatible result covers only the supplied pair, availability and operational constraints. Missing resource requirements not supplied by a caller cannot be discovered automatically. Venue suitability remains pending with the other team.
- Local precision/recall/F1 on these hand-designed cases show implementation agreement with fixtures. They do not estimate generalization or real-world vendor compatibility accuracy. Four pending cases are excluded from binary conflict metrics rather than treated as negatives.
- The evaluation timer measures in-process Python execution on a small fixture set. It is not production response time, load performance or an SLA.
- This code is intentionally not wired to FastAPI or React. No production behavior changed; existing backend regression and frontend build were outside this isolated Task 2 test scope.
