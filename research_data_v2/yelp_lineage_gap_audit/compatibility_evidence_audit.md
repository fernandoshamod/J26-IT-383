# Compatibility and operational evidence audit

**Evidence labels:** REAL_PUBLIC = directly traceable historical Yelp listing/review field; DERIVED = computed or classified from other data; SYNTHETIC_TEST = generated research fixture/assumption; UNKNOWN = no supporting observation. A populated CSV cell does not establish a vendor fact.

| Claim or field | Current evidence | Class | What can be concluded |
|---|---|---|---|
| Service-category pair compatibility | 15 rows in [vendor_compatibility_matrix.csv](../../vendor_compatibility_matrix.csv), scored 0–100; [service_compatibility.py](../../backend/engine/service_compatibility.py) averages known unordered category pairs | DERIVED | A static category heuristic. Catering + Entertainment = 80. This score is not a filter and says nothing about named vendor pairs. Some of the seven categories have no matrix pair, yielding unknown/partial scores. |
| Business identity, historical listing location/categories/reviews | Original local Yelp business/review JSONL, joined by business_id | REAL_PUBLIC | Historical public listing/review information, with source-file lineage; not confirmation of an event offering, service radius, or contract. |
| Seven service categories assigned to profiles | Preexisting classification using Yelp-like category/attribute fields | DERIVED / partly UNKNOWN | Classification logic is not fully recovered; a category label may be a proxy rather than a proven event service. |
| Simulated service area and supported event types | [build_hybrid_dataset.py](../../build_hybrid_dataset.py) copies profile city/state and gives every option Wedding; Corporate; Birthday | SYNTHETIC_TEST | Does not show actual travel radius or event-type acceptance. |
| Guest capacity | Each Catering option receives a random capacity from 50/100/150/200/300/500; other service types have no modelled capacity | SYNTHETIC_TEST for Catering; UNKNOWN for other services | A 500-person filter result is internal simulation only. No verified vendor capacity or scaling rule exists. |
| Estimated pricing | Random illustrative USD ranges per category/tier; fixed 330.777 conversion to LKR; billing rules | SYNTHETIC_TEST plus DERIVED conversion | Priceability under V1 is internal arithmetic, not an actual quote, tax, travel fee, or market rate. Yelp price_range is not a package quote. |
| Setup time, space, power, backup | Random values in option generator | SYNTHETIC_TEST | No inventory or venue feasibility evidence. |
| Vendor availability | 191 randomly assigned statuses for 30 SIMEVT templates | SYNTHETIC_TEST | New USER events have UNKNOWN date/time availability; [dynamic_feasibility.py](../../backend/engine/dynamic_feasibility.py) explicitly leaves it pending. | Vendor-pair collaboration/conflict | 330 random pair/event labels, marked `is_actual_collaboration=False` | SYNTHETIC_TEST | No verified prior cooperation or failure. USER-event pair checks are UNKNOWN/pending. |
| Shared crew/equipment | No V1 vendor resource inventory or assignment table | UNKNOWN | Can be tested with synthetic fixtures only. The isolated [PP1 conflict proof of concept](../pp1_task2_conflict_engine/README.md) is not production evidence. |
| Scheduling and travel conflicts | No current calendar, setup/teardown resource assignments, or travel evidence | UNKNOWN | USER-event dynamic feasibility leaves scheduling pending. |
| Venue constraints | Legacy [venue_constraints.csv](../../venue_constraints.csv) is header-only; sample event venue_status is Not evaluated | UNKNOWN | No venue capacity/access/power/space validation in this V1 path. |
| Operational risk / failure outcomes | Risk labels generated from review features; Random Forest predicts these rule labels | DERIVED | No independent service failure ground truth. Favorable risk score is not a calibrated booking failure probability. |

The production [dynamic package search](../../backend/engine/bounded_package_generator.py) uses the category compatibility score for ranking only when known. It does **not** eliminate category pairs as incompatible. A package with two distinct vendor IDs is not thereby a verified compatible vendor pair. For a USER event, the dynamic validator always records vendor collaboration, availability, scheduling, and venue suitability as verification requirements. The legacy header-only service detail/event/venue tables cannot fill those gaps.

Independent evidence to claim actual vendor compatibility would require dated, attributable, consented event records or confirmed vendor/organizer statements naming both vendor IDs, the shared event and role, outcome definition, source document, verification status, and adjudication. Evidence of resource sharing requires inventories and time-bound assignments; evidence of non-conflict requires interval coverage, not merely absence of a complaint. Contradictory or absent evidence should remain UNKNOWN.
